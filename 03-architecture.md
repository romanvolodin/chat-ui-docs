# Веб-чат: архитектура

В документе все решения приняты автором. Часть 1 — решения, озвученные автором. Часть 2 — рекомендации по реализации, предложенные ассистентом и затем утверждённые автором.

---

## Часть 1. Принятые решения

### 1. Три роли

| Роль | Что делает |
|---|---|
| **Интерфейс** | Только отображает полученные данные (списки чатов, переписку, информацию о пользователях и т.д.). Не знает, откуда данные берутся. |
| **Движок чата** | Используется, когда чат работает без приложения, которое поставляет данные. Хранит состояние и манипулирует данными; в киноинтерфейсе имитирует работу чата. |
| **Приложение** | Используется, когда чат встроен. Само создаёт, получает и меняет данные и передаёт их интерфейсу. |

### 2. Данные идут в интерфейс, действия — наружу

- Данные интерфейс получает снаружи и показывает столько, сколько выдали.
- Действия пользователя (отправить сообщение, создать группу, отметить прочитанным и т.д.) интерфейс только сообщает «наружу». Выполняет их тот, кто использует интерфейс: приложение или движок.
- Интерфейс ничего не знает об истории переписки. Когда пользователь докрутил до верха, интерфейс сообщает об этом, а приложение или движок решает, выдавать ли ещё часть истории и какого размера.

### 3. Доставка сообщений

Доставкой новых сообщений (мгновенно или периодическим обновлением) должно заниматься само приложение. Подробности отложены.

### 3а. Устройство в проектах и терминология

- **Паприка:** интерфейс (пакет) + фронтенд, который хранит состояние и шлёт запросы на бэкенд.
- **Киноинтерфейс:** интерфейс (тот же пакет) + движок чата, который хранит состояние и имитирует работу чата.
- Название «движок чата» выбрано вместо «ядро». Словом «бэкенд» эту часть не называют, потому что бэкенд ассоциируется с сервером и базой данных.
- Для движка чата нужен **отдельный репозиторий**, который импортирует пакет интерфейса.
- Диалоги для начала хранятся внутри движка чата: на старте это могут быть js-файлы и Mirage JS. Позже появится полноценный бэкенд. Mirage JS должен имитировать будущий бэкенд киноинтерфейсов (не бэкенд Паприки).

### 4. Режимы работы в проектах

| Проект | Источник данных |
|---|---|
| Паприка | Бэкенд: история выдаётся частями, поиск выполняется на бэкенде. |
| Киноинтерфейсы | Статические сайты без бэкенда: вся история загружается сразу, поиск и ответы собеседника имитируются по сценарию. |

### 5. Встраивание

- Встраивается чат целиком.
- Приложение показывает конкретный диалог (например, чат задачи) и даёт переход к списку чатов.
- Привязанные чаты создаёт приложение.
- Чат подстраивается под размеры произвольного блока.
- Пользователи приходят либо из собственной регистрации чата, либо из приложения-хозяина с его авторизацией.

### 6. Несколько экземпляров и стили

Чат может использоваться несколько раз, в том числе в рамках одного проекта, и у каждого экземпляра могут быть свои стили.

### 7. Пакет и репозиторий

- Интерфейс чата хранится в отдельном модуле/пакете и при необходимости импортируется в Киноинтерфейсы или в Паприку.
- Цель — делать обновления в одном месте.
- Пакет живёт в **отдельном репозитории**, потому что Паприка и Киноинтерфейсы напрямую не связаны.
- Репозиторий пока **приватный**.
- Способ доставки пакета в проекты должен быть простым, но с запасом на будущее.
- **Storybook** для проверки состояний интерфейса очень нужен.

### 8. Оформление

- Меняет разработчик, для начала правкой конфигов.
- В будущем — интерфейс для изменения стилей и тем любым человеком.
- Возможное изменение расположения элементов (время вне пузыря) считается сложным.

### 9. Стек (факты из обсуждения)

- Текущий chat-app: Vue 3, Pinia, Vue Router, VueUse, Vite.
- Паприка: Vue.js и Pinia.

### 10. Контракт

Подробно контракт между интерфейсом и движком или приложением описан в `06-contract.md`. Ключевые принципы, принятые автором:

- Контракт описывается на уровне корневого компонента `ChatRoot`.
- Какой чат открыт, хранит тот, кто использует интерфейс.
- Пользователи передаются по id и отдельным справочником, автор любого сообщения это запись справочника.
- Все длинные списки подгружаются по одному принципу, при переходе к далёкому сообщению снаружи выдают окно вокруг него.
- Нижнюю часть чата (поле ввода, кнопка звука, «Присоединиться» и др.) и подпись под названием чата указывает тот, кто отдаёт данные.
- Время приходит как момент времени, а «сейчас» для Киноинтерфейсов можно задать в настройках.

## Часть 2. Утверждённые рекомендации по реализации

Это предложения ассистента в ответ на вопрос «как реализовать». Автор утвердил их все.

1. **Пакет с компонентами**, собираемый Vite в режиме библиотеки, без знания о данных: данные приходят через props, действия уходят событиями.
2. **Состояние не глобальное.** В текущем chat-app состояние лежит в Pinia-сторах, общих для всего приложения. Если состояние живёт внутри экземпляра компонента, на одной странице можно держать несколько чатов.
3. **Темы через CSS-переменные**, заданные на корневом элементе конкретного чата. Темы можно хранить отдельными файлами или конфигами.
4. **Контейнерные запросы (`@container`)** вместо медиазапросов по ширине окна, чтобы раскладка зависела от размера блока.
5. **Слоты Vue и мелкое деление компонентов** для структурных различий (например, время вне пузыря). Вариант раскладки выбирается пресетом. Включать механизм можно позже, но делить компоненты стоит сразу.
6. **Доставка пакета из Git по тегам версий** (`v0.1.0`, `v0.2.0`…) с автосборкой через скрипт `prepare`. Заложить нормальное имя пакета, поле `exports` и semver, чтобы потом перейти на npm заменой одной строки. Для локальной разработки подключать пакет по пути (`npm link` или `file:`). При приватном репозитории сборка проектов требует доступа (SSH-ключ на локальной машине, токен для CI).
