# Веб-чат: пакет интерфейса и репозиторий

Документ описывает, как устроен пакет интерфейса чата `@romanvolodin/chat-ui`, что он экспортирует, как подключается к Киноинтерфейсам и Паприке и где живёт Storybook.

Источники: документы `01`–`06` и решения, принятые автором при обсуждении структуры пакета (10 ноября 2026).

## Как читать пометки

- **Решено** — принято автором.
- **Вывод** — вывод ассистента из принятых решений, требует проверки.
- **Знания ассистента** — общеизвестное поведение инструментов, не проверялось по актуальной документации.

Имена файлов и полей в коде нигде не зафиксированы. Примеры в документе помечены как иллюстрация.

## Границы документа

- Только пакет интерфейса и его репозиторий.
- Состав компонентов описан в `05-components.md`, контракт с движком чата в `06-contract.md`.
- Репозиторий движка чата Киноинтерфейсов, движок Паприки и формат хранения диалогов остаются отдельными темами.

## 2. Репозиторий

- Репозиторий `chat-ui` содержит один пакет. Storybook лежит внутри него как dev-зависимость (решено). Отдельные пакеты и монорепозиторий не обсуждались, исходники одного пакета лежат в `src/`.
- Репозиторий публичный с самого начала (решено).
  - Причина: Паприка задумана как open-source. Приватная зависимость не позволила бы другим людям собрать Паприку.
  - Следствие: для установки пакета не нужны ни SSH-ключи, ни токены, ни секреты в Docker-сборке Паприки.
- Лицензия пока не выбрана (решено). Пока лицензии нет, по умолчанию действуют все права автора. Выбрать лицензию нужно до открытия Паприки (вывод, см. раздел 12).
- Менеджер пакетов: npm везде. Альтернативы (pnpm, yarn) рассматривались: выгода от них проявляется в монорепозиториях, а работа pnpm с установкой из Git и `prepare` не проверялась (решено, остаёмся на npm).

## 3. Что экспортирует пакет

Публичная поверхность пакета намеренно маленькая (решено):

| Что | Назначение |
| --- | --- |
| `ChatRoot` | Корневой компонент, точка входа (см. `05-components.md`). |
| Типы контракта | Типы данных, props и событий `ChatRoot` (см. `06-contract.md`). Движок чата использует их как единый источник правды. |
| CSS-файл | Стили компонентов и тема по умолчанию. Подключается проектом отдельно. |

**Не экспортируются** внутренние компоненты (слои `base`, `message`, `area` из `05-components.md`). Решено.

- Контракт описан только на уровне `ChatRoot`, у внутренних компонентов публичных props и событий нет.
- Добавить экспорт позже можно без поломки проектов, а убрать или переименовать нельзя без новой мажорной версии (вывод из semver).
- Внутренности можно свободно делить и переименовывать без смены версии.
- Риск: панель оператора Киноинтерфейсов может потребовать базовых компонентов в стиле чата (кнопки, переключатели). Это решается, когда потребность появится.

Иллюстрация (не фиксирует имена файлов):

```ts
import { ChatRoot } from '@romanvolodin/chat-ui'
import type { /* типы контракта */ } from '@romanvolodin/chat-ui'
import '@romanvolodin/chat-ui/style.css' // имя файла условное
```

## 4. Зависимости и состояние

- **Vue 3 — peer-зависимость** (решено). Пакет объявляет `peerDependencies` с диапазоном подходящих версий Vue и не вшивает Vue в сборку. В проекте остаётся одна копия Vue. Если версия не подходит, npm предупреждает (знания ассистента).
- **Pinia не используется** (решено).
  - Состояние живёт внутри экземпляра чата, чтобы на одной странице можно было держать несколько чатов (см. `03-architecture.md`).
  - Все данные приходят от движка через props. В самом интерфейсе остаётся только локальное состояние (открытое меню, режим выделения, текст поиска, прокрутка), оно хранится средствами Vue (`ref`, `reactive`).
  - Общие значения внутри одного экземпляра передаются через `provide` и `inject` от `ChatRoot` (вывод, утверждено автором вместе с решением).
  - Единственная peer-зависимость пакета — Vue 3.
- **Движок чата** использует из `chat-ui` только типы контракта и объявляет `chat-ui` peer-зависимостью с диапазоном версий (решено). Версия `chat-ui` в проекте одна, и npm предупреждает о несовпадении.
- **Дубликат Vue при `npm link`.** Связанная локальная копия пакета может подтянуть собственный Vue, и компоненты ведут себя странно. Лечится настройкой `resolve.dedupe: ['vue']` в Vite проекта (знания ассистента, не проверено).

## 5. Стили, темы и изоляция

- **Стили** пакет отдаёт отдельным CSS-файлом, который проект подключает одной строкой (решено). Это поведение Vite в режиме библиотеки по умолчанию (знания ассистента).
- **Тема по умолчанию** лежит в пакете и является единственным справочником всех CSS-переменных (решено; последнее — вывод).
- **Переопределение темы.** Проект подключает свой CSS-файл, который задаёт значения переменных на корневом элементе экземпляра чата (классом или атрибутом). Для нескольких экземпляров с разными стилями на одной странице каждому корню задаётся свой класс или атрибут (решено).
- **Объект темы в `ChatRoot` не передаётся.** Добавим позже, когда возникнет необходимость, и не ломая существующие проекты (решено).
- **Слабое место:** опечатка в имени CSS-переменной не проверяется TypeScript и просто не сработает. Смягчается тем, что проекты копируют нужные строки из темы по умолчанию (вывод).
- **Изоляция стилей** обычным CSS (решено):
  - у всех классов чата общий префикс;
  - на корневом элементе сбрасываются унаследованные стили;
  - чат не стилизует голые теги вне своего контейнера;
  - внутри действуют только свои CSS-переменные.
- **Shadow DOM не используется.** Он усложнил бы подключение CSS-файлов и тем, вынос окон и меню в `body`, работу Storybook и тестов (знания ассистента). Защита обычным CSS не абсолютна: агрессивные глобальные стили страницы вроде `* { ... }` могут частично подхватиться. Если понадобится встраивать чат в чужие страницы, к Shadow DOM можно вернуться, но это, скорее всего, потребует новой мажорной версии (вывод).

## 6. Структура исходников

Исходники раскладываются по слоям из `05-components.md` (решено):

```
src/
  components/
    base/       базовые компоненты (Avatar, Button, Modal, ...)
    message/    компоненты сообщений (MessageBubble, ...)
    area/       области экрана (ChatSidebar, ChatView, ChatFooter, ...)
    ChatRoot.vue
  types/        типы контракта
  styles/       тема по умолчанию (CSS-переменные)
  index.ts      публичный экспорт
```

Иллюстрация, примеры названий компонентов условные.

- Истории Storybook предложено держать рядом с компонентами. Явного подтверждения по этому пункту не было (см. раздел 12).
- Рядом с `src/` в репозитории живут конфигурация Storybook, конфигурация сборки и описание проверок GitHub Actions. Точные имена файлов не фиксируются.

## 7. Сборка

- Сборка идёт Vite в режиме библиотеки (решено, `03-architecture.md`, часть 2, п. 1).
- **Формат — только ESM** (решено). Фронтенд Паприки и текущий chat-app собираются Vite. CommonJS нужен только старым инструментам и скриптам Node, таких потребителей нет. Каким сборщиком собираются сами Киноинтерфейсы, в обсуждении не называлось (см. раздел 14). Добавить CommonJS позже можно без поломки проектов (вывод из устройства поля `exports`).
- В `package.json` заложены нормальное имя пакета, поле `exports` и semver (решено, `03-architecture.md`), чтобы потом перейти на npm заменой одной строки.
- Типы для TypeScript генерируются при сборке. Нужен плагин, который выпускает файлы `.d.ts` и умеет работать с `.vue` (знания ассистента). Это единственная заметная настройка, которую TypeScript добавляет к сборке.
- Storybook и его зависимости в сборку для проектов не попадают (решено).

## 8. Версии и релизы

- Нумерация semver, теги вида `v0.1.0`, `v0.2.0` (решено, `03-architecture.md`).
- Старт с `0.1.0`. До стабилизации контракта остаёмся в `0.x`, где по правилам semver любой минорный выпуск может ломать совместимость. `1.0.0` выпускаем, когда контракт перестанет меняться (решено).
- Релиз — это тег в Git. Проект обновляется, когда в его зависимости меняется версия тега.

## 9. Доставка в проекты

**Решение: установка из Git по тегам** с автосборкой через скрипт `prepare` (решено).

Иллюстрация записи в `package.json` проекта (синтаксис по знаниям ассистента, не проверялся):

```json
{
  "dependencies": {
    "@romanvolodin/chat-ui": "github:romanvolodin/chat-ui#v0.1.0"
  }
}
```

Имя в ключе совпадает с именем пакета, поэтому импорты не зависят от способа доставки. Когда доставка сменится на npm, поменяется только значение.

Особенности (знания ассистента, не проверено):

- При установке из Git пакет собирается на машине проекта. Для этого npm ставит dev-зависимости пакета, в том числе тяжёлый Storybook. Установка медленнее, чем у готового пакета из реестра.
- В Docker-образе Паприки должен быть установлен `git`.

**Отвергнуто: GitHub Packages.** По документации GitHub (версия для Enterprise Server) и обсуждению сообщества на GitHub (проверено 10 ноября 2026, это не основная документация github.com) для установки npm-пакетов из GitHub Packages нужен токен доступа, даже для публичных пакетов. Поддерживаются только пакеты со scope. Токен вернул бы ту проблему доступа в Docker-сборке и локально, от которой избавил публичный репозиторий.

**Отложено: публикация в npmjs.com.** Вернёмся, когда Git начнёт мешать (например, из-за скорости установки). Пакет нужен только двум проектам автора, поэтому аккаунт в реестре и публикацию каждого релиза пока заводить не нужно (решено).

## 10. Подключение к проектам

| | Киноинтерфейсы | Паприка |
| --- | --- | --- |
| Где собирается | Пока только локально | Docker: на локальной машине для разработки и на сервере для продакшена |
| Сборщик | Не назывался (у текущего chat-app Vite, см. `03-architecture.md`) | Vite |
| Что подключает | `chat-ui` и движок чата напрямую | `chat-ui` и движок чата Паприки (её фронтенд) |
| Доступ к `chat-ui` | Публичный репозиторий, без токенов | Публичный репозиторий, без токенов |

**Цепочка в Киноинтерфейсах (решено).** Проект подключает `chat-ui` и движок чата **напрямую**, а не через движок. Связывает их сам проект:

1. движок хранит состояние и даёт данные;
2. проект передаёт их в `ChatRoot` через props и подписывается на события;
3. движок использует из `chat-ui` только типы контракта и объявляет пакет peer-зависимостью (см. раздел 4).

Минус: каждое приложение пишет небольшой связующий код. Смягчается тем, что движок может отдавать готовый набор props и обработчиков, типизированный по контракту (вывод).

**Один общий пакет «пока» (решено).**

- Сложная сценарная часть Киноинтерфейсов (подстановка реплик, управление сценарием, «нет связи» по команде) по принципу 9 в `06-contract.md` рисуется движком и в пакет не входит.
- Чату Паприки сейчас нужны: групповые чаты (позже и личные), ответы, пересылки, реакции, упоминания, загрузка картинок, видео и иногда файлов. Большая часть уже реализована, кроме упоминаний. Позже возможны закреплённые сообщения. Всё это есть в `02-requirements.md`.
- Минус общего пакета: в Паприке окажется больше кода, чем она использует, и сборка будет немного тяжелее (вывод).
- Вариант с отдельным упрощённым чатом для Паприки рассматривался и отложен.

## 11. Рабочий процесс разработки

Решение действует «пока» (решено):

1. **Основная разработка идёт в Storybook.** Изменения компонента видны сразу, без проекта и Docker.
2. **В проекты пакет попадает по тегам.** После правки ставится тег, в зависимостях проекта меняется версия.
3. **Проверка на живом проекте.**
   - Паприка (Docker): тег-кандидат (например, `v0.2.0-rc.1`) или временная зависимость от ветки (`github:romanvolodin/chat-ui#имя-ветки`). После новых коммитов в ветке пакет нужно переустановить. Папку с локальной машины в Docker не связываем.
   - Киноинтерфейсы (локальная сборка): временный `npm link` или `file:`. Для связанной копии нужна настройка `resolve.dedupe: ['vue']` (см. раздел 4).

## 12. Storybook

- Лежит в репозитории пакета как dev-зависимость и не входит в сборку, которая уходит в проекты (решено).
- **Публикуется на GitHub Pages автоматически через GitHub Actions при каждом пуше в основную ветку** (решено). Из-за этого на странице могут быть недоделанные состояния. Вариант «публиковать по тегу» рассматривался и не выбран.
- Что показывать (из `02-requirements.md`, `05-components.md`, `06-contract.md`): пустой чат, загрузку, «нет сети», ошибку отправки, разные типы чатов и сообщений. Для стабильных времён в историях используется замороженное «сейчас» (настройка, которая нужна и для Storybook).

## 13. Проверки в CI

На каждый пуш и пулл-реквест запускаются все проверки (решено):

- проверка типов (`vue-tsc`);
- сборка пакета;
- тесты (например, Vitest);
- линтер и форматирование.

Для автора, который только знакомится с TypeScript, проверка типов — главный помощник: ошибки в контракте находятся до сборки (вывод).

Отдельная публикация Storybook (раздел 12) настраивается тем же механизмом GitHub Actions.
